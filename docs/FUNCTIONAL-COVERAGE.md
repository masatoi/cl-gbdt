# Functional Coverage

Every symbol `cl-gbdt`, `cl-gbdt/lightgbm` and `cl-gbdt/xgboost` export has a position here:
either the functional suite's own sources name it, or a row below says why they do not.
`tools/ci/check-functional-coverage.lisp` fails the build when a published symbol has neither, so
a symbol cannot reach the public surface without the project taking a position on how it is
proven.

**Covered is not written down.** The checker derives it: a symbol is covered when it appears in
some top-level form of a `tests/functional/*.lisp` file, outside that file's own package form.
Recording it here as well would give it a second home to go stale in -- the same rule
`ffi-spec/BINDING-COVERAGE.md` follows for `wrapped`.

Neither are counts or percentages. Coverage in this project is guaranteed by classification --
every symbol has a recorded position -- not by a number. The checker prints the live counts on
every run.

**What being covered does NOT mean.** That the suite's source names a symbol is not that the
symbol's contract is exercised. A condition named in a `handler-case` clause counts. So does a
function called once inside a fixture nothing asserts on. This file records where every published
symbol stands; it does not measure how well anything is tested, and a green run is not evidence
that it does.

The heading a row sits under is part of what the checker reads. It recognises exactly two
spellings: the literal `## Unproven`, and any heading beginning `## Exempt`. A row under anything
else -- a renamed heading, a new one, or one preceding the file's first `## ` heading -- fails the
build rather than landing silently in either bucket.

Each `## Exempt` heading carries its section's argument, so a row's Note is for what the heading
does not already say. A symbol whose argument fits none of the headings belongs under
`## Unproven`; adding a heading also means editing the checker's vocabulary, which is a deliberate
act rather than a matter of writing prose.

Rows name the symbol the way `docs/API-REFERENCE.md` heads its entries -- qualified by the
shortest public package that exports it -- so a reader can move between the two files.

Notes are Markdown, so a code span closes with a backtick on both ends (`` `foo` ``); Lisp
source's `` `foo' `` convention -- an opening backtick and a closing apostrophe -- is not used
here, since an unclosed backtick leaves the rest of the row unrendered as code.

## Exempt: proven without a shared library

The symbol's whole contract is computation the shared library takes no part in, and the layer 1
suite proves it. A functional test here would open a library, ignore it, and assert what
`tests/*.lisp` already asserts -- three minutes of CI for no additional evidence.

A row belongs here only when the layer 1 test exists. "Nothing calls the library" is half the
argument; the Note carries the other half, by naming the test that does the proving.

## Exempt: an implementor's tool

Published for someone writing a backend, not for someone training a model. A functional test
would have to stand in for a backend to exercise it, which is what the backends themselves
already do on every functional run.

`with-pointer-ownership`'s own docstring states this about itself: "It is an implementor's tool,
not part of the everyday API -- a caller who only trains and predicts never reaches for it."
These rows are the rest of that category.

| Symbol | Who it is for |
|---|---|
| `cl-gbdt:write-foreign-sequence` | Copies a Lisp sequence into a foreign array through a caller-supplied coercer. Every real call site is inside a backend's own `native.lisp` -- LightGBM's `%set-dataset-field` and XGBoost's `%set-info-field` and `%set-group-field` -- and no test, layer 1 or functional, calls it by name; a caller who passes an array or a label vector to `make-dataset` reaches it without ever naming it, and every functional run that attaches a label exercises it that way. |
| `cl-gbdt:with-foreign-float-traps-masked` | Wraps the entire body of every `defmethod` in either backend's `protocol.lisp` and `classes.lisp`, and every exported `defun` in their `api.lisp` and `native.lisp` -- `tools/ci/check-float-traps.lisp` fails the build if one of them is missing it. A caller who trains or predicts never writes this macro; they get its effect automatically on every call into either library, and `CLAUDE.md` documents it as a rule backends themselves must follow. It has no dedicated test of its own: the SBCL-vs-C floating-point trap mismatch it corrects for -- confirmed by a real, once-uncaught `floating-point-invalid-operation` inside XGBoost's `multi:softprob` softmax on x86-64 -- is a property of the platform's trap configuration around a foreign call, not a value a layer 1 test could construct without one. |

## Exempt: an abstract condition its subclasses prove

A parent condition nothing signals directly. Functional tests catch its concrete subclasses, which
is the only way it is ever reached, so a test naming the parent would assert nothing the subclass
tests do not.

A row belongs here only when nothing signals the type itself. A parent that IS signalled somewhere
is a gap, not an abstraction.

| Symbol | Which subclasses prove it |
|---|---|
| `cl-gbdt:backend-error` | Nothing signals it directly -- `clgrep-search` across `src/` for `backend-error` finds only its own `define-condition`, its `backend-error-backend` reader, and every subclass's own `define-condition` naming it as their supertype. `src/conditions.lisp` defines it as the parent every backend-side failure inherits. Functional tests catch three of its concrete subclasses directly: `capability-unavailable` (e.g. `categorical-features-without-the-capability-signals`, `missing-value-without-the-capability-signals`, `sparse-input-without-the-capability-signals`, and their siblings across `tests/functional/`), `foreign-call-error` (e.g. `lightgbm-api-make-dataset-wrong-length-label-signals-without-leaking`), and `backend-not-open` (e.g. `lightgbm-api-operation-after-close-backend-signals-backend-not-open` and its ten siblings across both backends). |
