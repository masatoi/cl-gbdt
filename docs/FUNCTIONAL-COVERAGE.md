# Functional Coverage

Every symbol `cl-gbdt`, `cl-gbdt/lightgbm` and `cl-gbdt/xgboost` export has a position here:
either the functional suite's own sources name it, or a row below says why they do not.
`tools/ci/check-functional-coverage.lisp` fails the build when a published symbol has neither, so
a symbol cannot reach the public surface without the project taking a position on how it is
proven.

**Covered is not written down.** The checker derives it: a symbol is covered when it appears in
some top-level form of a `tests/functional/*.lisp` file, outside that file's own package form.
Recording it here as well would give it a second home to go stale in -- the same rule
`ffi-spec/BINDING-COVERAGE.md` follows for `wrapped`.

Neither are counts or percentages. Coverage in this project is guaranteed by classification --
every symbol has a recorded position -- not by a number. The checker prints the live counts on
every run.

**What being covered does NOT mean.** That the suite's source names a symbol is not that the
symbol's contract is exercised. A condition named in a `handler-case` clause counts. So does a
function called once inside a fixture nothing asserts on. This file records where every published
symbol stands; it does not measure how well anything is tested, and a green run is not evidence
that it does.

The heading a row sits under is part of what the checker reads. It recognises exactly two
spellings: the literal `## Unproven`, and any heading beginning `## Exempt`. A row under anything
else -- a renamed heading, a new one, or one preceding the file's first `## ` heading -- fails the
build rather than landing silently in either bucket.

Each `## Exempt` heading carries its section's argument, so a row's Note is for what the heading
does not already say. A symbol whose argument fits none of the headings belongs under
`## Unproven`; adding a heading also means editing the checker's vocabulary, which is a deliberate
act rather than a matter of writing prose.

Rows name the symbol the way `docs/API-REFERENCE.md` heads its entries -- qualified by the
shortest public package that exports it -- so a reader can move between the two files.

Notes are Markdown, so a code span closes with a backtick on both ends (`` `foo` ``); Lisp
source's `` `foo' `` convention -- an opening backtick and a closing apostrophe -- is not used
here, since an unclosed backtick leaves the rest of the row unrendered as code.

## Unproven

Symbols that should have a functional test and do not. This is the work list. Each Note says what
a test would have to do, which is what an order of work gets argued from.

| Symbol | What a functional test would have to prove |
|---|---|
| `cl-gbdt:version-range-verified-evidence` | `version-range-tested-description` reads this slot into every VERIFIED-labelled entry it formats, but no assertion in `tests/version.lisp` checks the evidence text a formatted entry carries -- `version-range-tested-description-distinguishes-verified-from-inferred` only greps for the low/high numbers, not the parenthesised evidence string. A test proving this needs nothing from a shared library: it only has to call `version-range-tested-description` (or the accessor directly) on a fixture with a known evidence string and assert that string appears in the result. |
| `cl-gbdt:version-range-inferred-evidence` | Same gap, on the INFERRED-labelled entry: `version-range-tested-description` reads this slot too, and no assertion checks the inferred evidence text it produces. Also provable at layer 1 with no library -- the same kind of direct assertion as above, on the second entry `version-range-tested-description` returns. |
| `cl-gbdt:*lightgbm-version-range*` | Read by nothing but its own docstring and `src/version.lisp` itself -- `clgrep-search` across `src/` finds it named only in `version.lisp`'s own definition and, in prose, inside `lightgbm/classes.lisp`'s `initialize-backend` docstring, never in that method's code. Its own docstring states why: LightGBM's C API has no version entry point, `backend-version` is always NIL there, and `check-backend-version` is never called for this backend, so nothing -- no functional test, no layer 1 test, no runtime code path at all -- can compare a real library against this range. It is recorded for documentation only; there is no behavior left to prove. |
| `cl-gbdt:*xgboost-version-range*` | Read only by `xgboost/classes.lisp`'s `initialize-backend`, which passes it to `check-backend-version` right after reading the just-opened library's real version -- so proving this variable's recorded bounds match the vendored library means opening the real XGBoost backend and asserting `open-backend :xgboost` (or an equivalent functional fixture) signals no `untested-backend-version` warning. No test today, layer 1 or functional, references `*xgboost-version-range*` by name, even though every functional test that opens the XGBoost backend exercises it at runtime. |
| `cl-gbdt:csr-matrix-indices` | Read by both backends' real code -- `lightgbm/api.lisp`'s and `xgboost/api.lisp`'s `%dataset-pointer`, and `xgboost/api.lisp`'s `predict` -- to pin a `csr-matrix`'s column indices before handing them to the library, and `tests/functional/sparse-input.lisp` builds real `csr-matrix` instances and predicts against both real backends, so a badly broken reader would likely fail those tests. But no test, layer 1 or functional, calls `csr-matrix-indices` and checks what it returns, or isolates INDICES from its three siblings (INDPTR, VALUES, NUM-COLUMNS) the way `csr-matrix-reports-its-shape` does for them: that test checks NUM-COLUMNS, NUM-ROWS, VALUES and INDPTR's type, and never mentions INDICES; `csr-matrix-slots-are-read-only` only confirms the symbol names a function with no `setf` writer. A test proving this needs nothing from a shared library: a fixture built with known indices, read back through `csr-matrix-indices` and compared with `equalp` -- the same shape `csr-matrix-reports-its-shape` already uses for VALUES -- would close the gap without opening either library. |

## Exempt: proven without a shared library

The symbol's whole contract is computation the shared library takes no part in, and the layer 1
suite proves it. A functional test here would open a library, ignore it, and assert what
`tests/*.lisp` already asserts -- three minutes of CI for no additional evidence.

A row belongs here only when the layer 1 test exists. "Nothing calls the library" is half the
argument; the Note carries the other half, by naming the test that does the proving.

| Symbol | What proves it instead |
|---|---|
| `cl-gbdt:version-compare` | Orders two version strings and touches nothing else. `tests/version.lisp` covers each ordering, equal versions, differing component counts, and both malformed operands, in `version-compare-orders-by-component` and `version-compare-rejects-unparseable-input`. |
| `cl-gbdt:version-in-range-p` | Compares a version against two bounds via `version-compare` alone. `tests/version.lisp`'s `version-in-range-p-covers-inside-and-both-boundaries` proves both inclusive boundaries and a single-point range; `version-in-range-p-covers-below-and-above` proves both out-of-range directions; `version-in-range-p-cannot-confirm-unparseable-or-nil` proves an unparseable or NIL version or bound returns NIL rather than a false confirmation. |
| `cl-gbdt:check-backend-version` | Compares a version string against a range's *inferred* bounds and conditionally `warn`s; never touches a library itself, only ever called (at runtime) by XGBoost's `initialize-backend`. `tests/version.lisp`'s five `check-backend-version-*` tests, using a fixture range and `handler-bind`-collected warnings, prove: no warning inside the inferred range including both boundaries (`check-backend-version-does-not-warn-inside-the-inferred-range`); a warning below it, carrying the right backend, version and tested-description (`check-backend-version-warns-below-the-inferred-range`); a warning above it (`check-backend-version-warns-above-the-inferred-range`); a warning on an unparseable version (`check-backend-version-warns-on-unparseable-version`); and a warning on a NIL version (`check-backend-version-warns-on-nil-version`). |
| `cl-gbdt:make-version-range` | Constructs a `version-range` record from its six keyword slots. Six `deftest` forms in `tests/version.lisp` actually call it: five reach it indirectly through the `%fixture-range` helper (`check-backend-version-does-not-warn-inside-the-inferred-range`, `check-backend-version-warns-below-the-inferred-range`, `check-backend-version-warns-above-the-inferred-range`, `check-backend-version-warns-on-unparseable-version`, `check-backend-version-warns-on-nil-version`), and `version-range-tested-description-distinguishes-verified-from-inferred` calls it both through that same helper and again directly, to build a second range with distinct VERIFIED bounds. A keyword constructor does not depend on argument order; what these tests would actually catch is a renamed or dropped keyword. |
| `cl-gbdt:version-range` | The record type `make-version-range` builds; every instance of it in `tests/version.lisp` flows only into `check-backend-version` or `version-range-tested-description`, never anything else. Proven by the same six tests as `make-version-range` (see that row) -- the five `check-backend-version-*` tests via `%fixture-range`, plus `version-range-tested-description-distinguishes-verified-from-inferred`, which also builds a second instance directly -- both construct and consume an instance with exactly its six documented slots. |
| `cl-gbdt:version-range-verified-low` | Read into the VERIFIED-labelled entry `version-range-tested-description` formats. `version-range-tested-description-distinguishes-verified-from-inferred`'s first case uses a fixture with VERIFIED-LOW = VERIFIED-HIGH = `"3.3.0"` and asserts the formatted entry contains `"3.3.0 verified"`; its second case uses VERIFIED-LOW = `"4.0.0"` (distinct from VERIFIED-HIGH) and asserts the entry contains `"4.0.0-4.7.0 verified"`, which only holds if this accessor returns exactly `"4.0.0"`. |
| `cl-gbdt:version-range-verified-high` | Same mechanism as `version-range-verified-low`, proven by the same two cases in `version-range-tested-description-distinguishes-verified-from-inferred`: the first case's fixture sets VERIFIED-HIGH equal to VERIFIED-LOW and asserts the dash is omitted (`(ng (search "3.3.0-3.3.0" ...))`); the second sets VERIFIED-HIGH = `"4.7.0"`, distinct from VERIFIED-LOW, and asserts the entry contains `"4.0.0-4.7.0 verified"`, which only holds if this accessor returns exactly `"4.7.0"`. |
| `cl-gbdt:version-range-inferred-low` | Read into the INFERRED-labelled entry `version-range-tested-description` formats. `version-range-tested-description-distinguishes-verified-from-inferred`'s first case uses a fixture with INFERRED-LOW = `"1.7.0"`, INFERRED-HIGH = `"3.3.0"`, and asserts the second formatted entry contains `"1.7.0-3.3.0 inferred"`, which only holds if this accessor returns exactly `"1.7.0"`. |
| `cl-gbdt:version-range-inferred-high` | Same case as `version-range-inferred-low`: `version-range-tested-description-distinguishes-verified-from-inferred`'s assertion that the second formatted entry contains `"1.7.0-3.3.0 inferred"` only holds if this accessor returns exactly `"3.3.0"`, the fixture's INFERRED-HIGH. |
| `cl-gbdt:version-range-tested-description` | Formats a range's VERIFIED and INFERRED bounds as two evidence strings. `tests/version.lisp`'s `version-range-tested-description-distinguishes-verified-from-inferred` proves the no-dash case (VERIFIED-LOW = VERIFIED-HIGH) and the dashed case (VERIFIED-LOW /= VERIFIED-HIGH); `check-backend-version-warns-below-the-inferred-range` proves its return value is exactly what `untested-backend-version`'s `:tested` initarg receives when `check-backend-version` warns. |
| `cl-gbdt:normalize-parameters` | Turns a keyword plist into backend key/value string pairs and touches nothing else. `tests/parameters.lisp` covers name conversion to snake_case (`normalize-parameters-returns-name-value-pairs`), the odd-length-plist error (`normalize-parameters-rejects-odd-length-plist`), double-float, single-float and small-double-float printing without a type marker (`normalize-parameters-prints-double-float-without-a-type-marker`, `-single-float-`, `-small-double-float-`), ratio-to-decimal conversion (`normalize-parameters-prints-a-ratio-as-a-bare-decimal`, `-prints-a-ratio-as-a-decimal`), T/NIL as `"true"`/`"false"` (`normalize-parameters-prints-booleans-as-true-and-false`), and independence from the caller's `*print-base*` (`normalize-parameters-output-is-independent-of-the-caller-s-print-base`). |
| `cl-gbdt:csr-matrix` | The record type `make-csr-matrix` builds; `tests/data.lisp`'s CSR suite builds every instance through `%csr`, a thin wrapper over `make-csr-matrix`, and every instance flows only into this type's own readers, never into either library. Thirteen `deftest` forms exercise it: `csr-matrix-reports-its-shape` builds one and reads several slots back (see the individual reader rows below); nine `csr-matrix-rejects-*` tests and `csr-matrix-accepts-any-sequence` build and validate at construction time; `csr-matrix-allows-an-all-zero-trailing-column` and `csr-matrix-allows-an-empty-row` build and read back two more legal shapes; `csr-matrix-slots-are-read-only` confirms all four accessors exist with no `setf` writer. |
| `cl-gbdt:csr-matrix-indptr` | `csr-matrix-reports-its-shape` asserts its return value is coerced to exactly the `(simple-array (signed-byte 32) (*))` type `%coerce-index-vector` promises. Its LENGTH -- what `csr-matrix-num-rows` derives from it -- is proven for three different INDPTR inputs by that same test (length 3 -> 2 rows), `csr-matrix-accepts-any-sequence` (a vector INDPTR of length 3 -> 2 rows), and `csr-matrix-allows-an-empty-row` (length 4 with one repeated entry -> 3 rows). No test asserts the individual elements survive `make-csr-matrix`'s coercion unchanged -- only the type, and the length `csr-matrix-num-rows` depends on. |
| `cl-gbdt:csr-matrix-values` | `csr-matrix-reports-its-shape` asserts both its exact content -- `(equalp #(1.0d0 2.0d0 3.0d0) (cl-gbdt:csr-matrix-values m))` against the VALUES `%csr`'s default fixture builds -- and that it was coerced to `(simple-array double-float (*))`. |
| `cl-gbdt:csr-matrix-num-columns` | Asserted directly in two tests: `csr-matrix-reports-its-shape` (`(= 3 (cl-gbdt:csr-matrix-num-columns m))` against the default fixture's NUM-COLUMNS of 3) and `csr-matrix-allows-an-all-zero-trailing-column` (`(= 3 ...)` after building with an INDICES sequence that never reaches column 2, proving the declared width comes back rather than one inferred from the stored indices). |
| `cl-gbdt:csr-matrix-num-rows` | Asserted directly in three tests, each against a different INDPTR length: `csr-matrix-reports-its-shape` (`(= 2 ...)`, INDPTR length 3), `csr-matrix-accepts-any-sequence` (`(= 2 ...)`, a vector INDPTR of length 3), and `csr-matrix-allows-an-empty-row` (`(= 3 ...)`, INDPTR length 4 with a repeated entry for the empty row). |
| `cl-gbdt:foreign-element-type` | Maps `double-float`/`single-float` to `:double`/`:float` and touches nothing else. `foreign-element-type-maps-to-cffi-keywords` asserts both mappings directly; the `unsupported-element-type` condition it signals for anything else is exercised one layer up, through `with-foreign-matrix`, by `unsupported-element-type-is-rejected`. |
| `cl-gbdt:foreign-matrix` | The class `call-with-foreign-matrix` has a passthrough method for -- per that method's own docstring, "MATRIX is already foreign memory ... FUNCTION receives MATRIX's own pointer, dimensions and element type unchanged, with no copy and no pin." `foreign-matrix-is-passed-through` builds one via `make-instance` over a `cffi:with-foreign-object` buffer it owns, hands it to `with-foreign-matrix`, and asserts the pointer that comes back is `cffi:pointer-eq` to its own buffer -- proving no copy happened -- alongside both dimensions and the element type: the whole class exercised with neither library involved. |
| `cl-gbdt:foreign-matrix-pointer` | Read by `call-with-foreign-matrix`'s `foreign-matrix` method to hand FUNCTION the stored pointer unchanged. `foreign-matrix-is-passed-through` asserts the pointer `with-foreign-matrix` binds is `cffi:pointer-eq` to the exact buffer the instance was constructed with, which only holds if this reader returns it unchanged. |
| `cl-gbdt:foreign-matrix-rows` | Same mechanism and test as `foreign-matrix-pointer`: `foreign-matrix-is-passed-through` constructs an instance with `:rows 2` and asserts the NROW `with-foreign-matrix` binds is `2`, which only holds if this reader returns exactly what was stored. |
| `cl-gbdt:foreign-matrix-cols` | Same mechanism as `foreign-matrix-rows`: `foreign-matrix-is-passed-through` constructs an instance with `:cols 2` and asserts the NCOL `with-foreign-matrix` binds is `2`. |
| `cl-gbdt:foreign-matrix-element-type` | Same mechanism again: `foreign-matrix-is-passed-through` constructs an instance with `:element-type 'double-float` and asserts the ELEMENT-TYPE `with-foreign-matrix` binds is `eq` to `'double-float`. |
| `cl-gbdt:call-with-foreign-matrix` | Neither backend calls this generic function by name -- both reach it only through the `with-foreign-matrix` macro, which is what `tests/data.lisp` calls directly in every one of its eight matrix-handling tests, proving both defined methods and the branch inside the `array` one: `double-matrix-is-passed-row-major`, `single-matrix-is-passed-row-major` and `large-matrix-round-trips` exercise the SBCL pinned path over a `simple-array`; `non-simple-array-is-copied` exercises the copy fallback over an adjustable array; `pinned-matrix-survives-garbage-collection` proves the pinned pointer survives a full GC while held; `unsupported-element-type-is-rejected` and `wrong-rank-is-rejected` prove its two validation errors; `foreign-matrix-is-passed-through` proves the `foreign-matrix` method (see that row above). None of this reaches either shared library -- it is CFFI/SBCL memory management that runs identically whether or not LightGBM or XGBoost is even installed. |
| `cl-gbdt:check-foreign-call` | Never calls a library itself: CODE is a plain integer and LAST-ERROR is an opaque thunk supplied by the caller, the same shape as `check-backend-version` above -- it "never touches a library itself, only ever called (at runtime) by" each backend's own `check-lgbm`/`check-xgb` wrapper. Three `deftest` forms in `tests/foreign.lisp` supply fake thunks and prove the whole contract directly: `check-foreign-call-returns-the-code-on-success` proves a zero CODE returns it and never calls LAST-ERROR; `check-foreign-call-signals-on-failure` proves a nonzero CODE signals `foreign-call-error` carrying FUNCTION-NAME, CODE and LAST-ERROR's result; `check-foreign-call-tolerates-a-nil-message` proves a LAST-ERROR returning NIL still produces a report -- `"(no message)"` -- rather than a broken one. |

## Exempt: an implementor's tool

Published for someone writing a backend, not for someone training a model. A functional test
would have to stand in for a backend to exercise it, which is what the backends themselves
already do on every functional run.

`with-pointer-ownership`'s own docstring states this about itself: "It is an implementor's tool,
not part of the everyday API -- a caller who only trains and predicts never reaches for it."
These rows are the rest of that category.

| Symbol | Who it is for |
|---|---|
| `cl-gbdt:write-foreign-sequence` | Copies a Lisp sequence into a foreign array through a caller-supplied coercer. Every real call site is inside a backend's own `native.lisp` -- LightGBM's `%set-dataset-field` and XGBoost's `%set-info-field` and `%set-group-field` -- and no test, layer 1 or functional, calls it by name; a caller who passes an array or a label vector to `make-dataset` reaches it without ever naming it, and every functional run that attaches a label exercises it that way. |
| `cl-gbdt:with-foreign-float-traps-masked` | Wraps the entire body of every `defmethod` in either backend's `protocol.lisp` and `classes.lisp`, and every exported `defun` in their `api.lisp` and `native.lisp` -- `tools/ci/check-float-traps.lisp` fails the build if one of them is missing it. A caller who trains or predicts never writes this macro; they get its effect automatically on every call into either library, and `CLAUDE.md` documents it as a rule backends themselves must follow. It has no dedicated test of its own: the SBCL-vs-C floating-point trap mismatch it corrects for -- confirmed by a real, once-uncaught `floating-point-invalid-operation` inside XGBoost's `multi:softprob` softmax on x86-64 -- is a property of the platform's trap configuration around a foreign call, not a value a layer 1 test could construct without one. |
